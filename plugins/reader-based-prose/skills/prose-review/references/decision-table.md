# 決策表：每個詞怎麼處理

依「定義的來源」與「在文件中的角色」決定。不要一律刪除代號：有些代號是索引，刪掉會遺失資訊。

## 依定義來源

| 定義來源 | 裁決 |
|---|---|
| repo 的 glossary | 視為已定義；repo 內文件可用連結，離開 repo 的文字補一句白話 |
| 業界通用 | 保留，首次出現時加括號說明 |
| 團隊規則檔 | 保留代號當索引，同時寫出內容 |
| 只存在對話 | 刪除並改寫成白話，或先登錄進 glossary（附來源）再引用 |
| 不明 | 標【待補】並詢問使用者 |

範例：

- 業界通用：`P50` 寫成 `P50（中位數估計，有一半機會在此時數內完成）`。
- 團隊規則檔：寫成 `開工前和 PM 對齊預算的三個問題（團隊規則 BUDGET-1）`。也可以把代號登錄到 `.prose-check.json` 的 `known_terms`，並附上可開啟的來源路徑。
- 只存在對話：`Q1～Q4` 改寫成「事實、不處理會怎樣、可能性、誰負責」。
- 不明：寫成 `Apollo【待補：是什麼、為何單獨列出】`。

判準：**加註的前提是有可回溯的來源**。來源只是一段對話時，註解等於指向讀者打不開的地方。

## 依問題類型

| 類型 | 辨識方式 | 處理 |
|---|---|---|
| 私有定義 | 冷讀者理解與原意不同 | 換成不會誤讀的詞，或首次出現時定義 |
| 術語碰撞 | 兩個詞指涉接近 | 改成能區分的名稱 |
| 範例需要解碼 | 範例本身含多層代號 | 改用白話描述的具體情境 |
| 圈號引用 | 數字圈號指向某份清單 | 說明清單出處，或寫出該項內容 |
| 對話殘留 | 文字指向對話 | 把內容寫進文件 |

範例：

- 私有定義：`上限` 實指「風險全部發生時的總時數」，改成「最壞情況時數」。
- 術語碰撞：`未判定` 指可能性未查證，`⚪` 指嚴重性未評估；改名為「可能性未查證」與「嚴重性未評估」。
- 範例需要解碼：`No.17 的 F-xx` 要查三層才知道是什麼，改寫成「第 17 張表單施工時發現的問題」。
- 圈號引用：`判準 ①`。
- 對話殘留：`本次對話`、`as discussed`。

## 代號保留的例外

代號在文件中被引用三次以上時，它是索引，不是雜訊：保留，在首次出現處定義即可。
