讀者手上只有這張表

reader-based-prose 是一個 Claude Code plugin。它讓 AI 寫給人看的文字，不用查詢、不用看對話紀錄就能讀懂，同時不遺失細節。

下面這張表是 AI 在一個 session 中產出的，用來說明團隊流程和 SDD 的差異。下面保留原表的結構與問題，團隊專屬代號已換成中性說法。點選表格中標記的詞，看讀者能去哪裡查。

補了名詞表之後，問題反而更清楚

讀者看不懂，於是請 AI 補一張名詞表。上面點選後顯示的「名詞表怎麼寫」，就是那張名詞表的內容。它本身暴露出六個問題：

問題名詞表裡的證據讀者的後果
定義留在對話裡註明 本次對話自創讀者沒有地方可查
日常詞帶私有意思上限 指風險全發生時的時數讀錯了也不會察覺
兩個詞指涉重疊未判定 與 ⚪兩件事被讀成一件
範例需要解碼「前案表單的某條發現」要查三層範例反而更難懂
名詞表有漏SDD、「某份開發報告」、回測 沒列AI 自列的表不可靠
定義和使用分開名詞表是另一張表每讀一格就要跳一次

第二與第三個問題最危險。遇到代號，讀者至少會停下來查；遇到「上限」這種日常詞，讀者會照日常意思理解，而且不知道自己讀錯了。未判定 指的是「還不知道會不會發生」，⚪ 指的是「還不知道有多嚴重」，原表卻把兩者寫成同一個詞組。

為什麼 AI 特別容易這樣寫

 模型的 context（看得到）             讀者手上的文件（看不到）
┌──────────────────────────┐        ┌──────────────────────────┐
│ 對話中取的四項風險提問     │        │                          │
│ 計畫裡的某項預算檢查       │──寫出──▶│ 「四項風險提問、未判定」   │
│ 前面回合定義的「未判定」   │        │     ↑ 定義沒跟著進來      │
└──────────────────────────┘        └──────────────────────────┘

模型寫作時，context 裡有對話、計畫與子任務回報，這些內容讀者都看不到。代號的定義留在對話裡，文件只帶走代號。寫作研究稱這種文字為作者本位文字（writer-based prose，Flower 1979）：作者把自己的思考過程原樣交出，使用只對自己有意義的代號詞。名詞表上的 本次對話自創 是這個機制的直接證據。

修正也會失敗

最直覺的修法是把定義全部塞回表格。這樣每一格都讀得懂了，但表格失去比較功能：

定義壓縮成代號

結算單：P50、上限、某項預算檢查

格子短，但讀不懂。

定義塞回格子

每份規格附結算單：中位數估計時數（P50，有一半機會在這個時數內完成）、最壞情況時數（估工檔列出的風險全部發生時），以及開工前和 PM 對齊預算的三個問題（某項預算檢查）

讀得懂，但無法比較。

所以問題不在代號多寡，而在代號與定義放錯地方。這個 plugin 不是「刪代號」的工具：它依每個詞的定義來源決定保留、加註或改寫，並把比較和解釋分成兩層。

同樣的問題也出現在對話回覆

給人看的回覆也會這樣寫。例如一則回覆寫著 直接證實了上一輪的根因 B：根因 B 是 AI 在前一則回覆裡自己取的代號，讀者只能往上捲去找。回覆的讀者雖然在對話裡，但人的記憶不像模型的 context 那樣完整：掃讀過、切去別的工作、隔幾小時才回來。

設計理念

九條原則分成四組。每一條都附上在 plugin 裡的做法，以及它從哪個失敗學來。

判準：讀者能不能讀懂

讀者只拿到文件。讀者能用的資源是文件本身、名詞表、可開啟的連結；不包括寫作當時的對話。所以冷讀者只拿得到檔案路徑與名詞表路徑，拿不到任何背景說明。附上背景，冷讀者就和作者一樣知道太多，測試失效。

要降低的是推論量，不是資訊量。把定義塞回表格，資訊都在，卻失去比較功能。所以 plugin 不刪代號，而是依來源決定保留、加註或改寫，並把比較和解釋分成兩層。

修正：依定義的來源決定

加註的前提是可回溯的來源。對話中自創的代號，加註也只是指向讀者打不開的地方。所以只存在對話的代號必須改寫，或先登錄進名詞表再引用；known_terms 登錄的路徑必須存在；名詞表的條目要附來源。

不知道就標【待補】。替代號編一個看似合理的定義，比留白更危險，因為讀者無從察覺它是猜的。所以 plugin 遇到不懂的代號，只標【待補】並詢問使用者。

檢查：便宜的先做，昂貴的只在必要時做

規則判得出的，不靠實測。早期設計對每個代號都做「保留與改寫」兩版比較，套到實際案例後才發現，決定裁決的幾乎都是定義來源，比較測試沒有發揮作用，還看不到格子過長這類問題。所以版本比較只用在決策表判不出的情況，以及離線校準規則。

規則抓不到的，交給看不到對話的讀者。「上限」這類日常詞的私有意思，規則比對抓不到。所以第二階段讓冷讀者用自己的話複述每個詞，再和作者原意比對。

介入：不製造新的混亂

已經顯示的文字不阻擋，只記錄。回覆已經出現在畫面上，阻擋只會讓 Claude 在後面再補一段更正。所以文件檢查會回饋給 Claude 修正，因為檔案還能改；回覆檢查只寫紀錄，定期彙整後再回頭補進預防規則。

輔助資源是選用的。不是每個 repo 都有名詞表。所以找不到名詞表就略過，只有設定檔明確指定、檔案卻不存在時才回報。

自己的文件要通過自己的檢查。用 plugin 檢查它自己的文件，抓到了 checker 把範例中的指令當成真指令的 bug，也抓到了作者本人寫出過長的表格格子。所以每次修改都要重跑檢查與測試，evals/fixtures 的正負樣本是規則的回歸測試。

Workflow

整體流程

流程裡有兩個迴圈，以強調色標示。內圈在單一檔案上運作：寫入、檢查、修正、再寫入，直到沒有發現。外圈跨 session 運作：回覆檢查的紀錄經過彙整，把高頻出現的代號登錄進名詞表、補進預防規則，下一個 session 開始時就會注入。

prose-review 的三個階段

  1. 第一階段：規則比對列出代號、對話殘留、過長格子。
  2. 第二階段：冷讀者複述冷讀者只拿到檔案與名詞表路徑，用自己的話複述每個詞；和作者原意比對，找出私有意思與術語碰撞。
  3. 決策表判得出？判得出就直接裁決，並附上依據的規則；判不出才進入第三階段。
  4. 第三階段：版本比較冷讀者比較「保留代號加註」與「改寫成白話」兩個版本。

規則比對抓得到代號，抓不到日常詞的私有意思，所以需要冷讀者：一個只拿到文件、看不到對話的讀者，用自己的話複述每個詞，再和作者原意比對。

範圍外原因

文字是否優美目標是讀懂，不是好看

成功的樣子

讀者拿到文件，不用查詢、不用看對話紀錄就能讀懂，細節也沒有遺失。要壓低的是讀者必須自行重建的推論量，不是資訊量。可量測的指標有兩個：每千字的未定義代號數，以及冷讀者的理解正確率。

第一階段辨識的代號樣式：大寫加數字（P50、XYZ-100）、範圍（T1～T4）、全大寫縮寫（SDD）、編號（No.42）、圈號（規則 ①）、狀態符號（⚪），以及「方案、根因、選項」等固定前綴接單一大寫字母（方案 B）。這些是虛構的樣式範例，不是任何真實專案的內部詞。

名詞表（選用）

repo 裡有名詞表（glossary）時，plugin 把它當成讀者打得開的定義來源；沒有時略過，不報錯。

情況行為
自動搜尋到名詞表裡面的詞視為已定義，並注入詞彙清單
找不到名詞表略過，其餘檢查照常
設定檔指定的名詞表不存在回報，因為這代表設定寫錯
名詞表有來源欄，條目沒填編輯名詞表時回報

詞彙清單在 session 開始時注入 context，引導 Claude 使用既有的詞，不另取同義詞。要長期使用的新詞，先登錄進名詞表並附來源，再在文件中引用。

自動搜尋的檔名或目錄名（不分大小寫）：glossary、terms、terminology、ubiquitous-language、名詞、名詞表、名詞庫、詞彙、詞彙表、術語、術語表。搜尋深度四層，略過 .git、node_modules、bin、obj 等建置目錄。支援三種條目格式：表格第一欄、- **詞**：定義、### 詞 標題。

回覆檢查

回覆的判準不是「有沒有定義」，而是「代號是誰提出的」：

代號來源判定
使用者用過的詞、名詞表的詞放行
模型提出、這則回覆有定義放行
模型提出、這則回覆沒定義記為模型自創代號
引用這則回覆裡沒有的章節編號記為跨回合引用

範例：根因 B 屬於第三列，依 4.1 屬於第四列。

回覆已經顯示在畫面上，阻擋只會讓 Claude 在後面再補一段更正，所以只寫紀錄到 .prose-check/console-log.jsonl。定期執行 python3 scripts/prose_check.py --report 查看高頻問題，再把高頻的詞登錄進名詞表，或補進預防規則。

需求與設定

Python 3.9 以上，不需要額外套件。在專案根目錄放 .prose-check.json（全部欄位都可省略）：

{
  "mode": "feedback",
  "include": ["**/skills/**/*.md", "**/docs/**/*.md"],
  "exclude": ["**/CHANGELOG.md"],
  "max_cell_chars": 40,
  "allow_terms": ["MediatR"],
  "known_terms": { "XYZ-100": "docs/rules/budget.md" },
  "glossary_files": [],
  "console_mode": "log"
}
欄位作用
modefeedback 回饋給 Claude；off 停用
include、exclude檢查範圍，相對於設定檔所在目錄
max_cell_chars表格單格字數上限
allow_terms讀者一定認得、不需要定義的詞
known_terms規則檔中有定義的代號與來源路徑
glossary_files指定名詞表路徑；空清單代表自動搜尋
glossary_autodiscover設為 false 停用自動搜尋
console_modelog 寫回覆檢查紀錄；off 停用
console_log紀錄檔路徑

known_terms 登錄的來源路徑不存在時會被回報。檔案內的指令：<!-- prose-check: ignore 詞1, 詞2 --> 忽略特定詞；<!-- prose-check: off --> 整份不檢查。環境變數 PROSE_CHECK_DISABLE=1 會暫停 hook。

手動執行與測試

python3 scripts/prose_check.py docs/foo.md          # 人看的報告；有發現時 exit 1
python3 scripts/prose_check.py docs/foo.md --json   # 結構化輸出
python3 scripts/prose_check.py --report             # 彙整回覆檢查紀錄
python3 -m unittest tests/test_prose_check.py       # 驗證規則

evals/fixtures 有三份樣本：參照斷裂的表格、定義全塞進格子的表格、兩層結構的正面範例。調整規則前先在這裡加樣本。

已知限制

第一階段以規則比對，小寫的自創詞（例如 work-log）抓不到，交給第二階段。「詞（說明）」與「說明（詞）」兩種寫法都視為已定義；說明內容是否正確，要靠第二階段確認。回覆檢查讀的是 transcript 檔；Claude Code 若改變 transcript 格式，這部分需要跟著調整。紀錄檔是否進版控由團隊決定；不想進版控就把 .prose-check/ 加進 .gitignore。
